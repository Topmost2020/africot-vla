# Stage S7: Integration

## Purpose and place in the architecture

The AfriCoT-VLA design couples the slow loop (renderer, vision-language-action model, subgoal validator and coordinator) to the fast loop (world model, CEM planner and shield) through the subgoal (`SPEC.md`, `docs/design.html`). Stage S7 assembles these parts into the `africot_full` controller and checks the wiring end to end with the mock VLAM backend. The mock backend is deterministic and rule-based, and the specification allows it only for tests and wiring, so the stage produces no reportable VLAM result.

## What was built

The integration check was committed in `06dfee7`, and the mock-wiring results and example logs in `6aeb842`. The components it exercises were built in the stage on the slow loop (`7c0d5df`): `africot/coordinator.py`, `africot/renderer.py`, `africot/vlam.py`, `africot/subgoal.py` and `africot/log.py`.

- `sim/check_integration.py`, which runs `africot_full` with the mock backend on all four scenarios and evaluation seeds 0 to 4 (20 runs) and writes `results/mock_wiring/s7_integration_check.json`.
- Mock results in `results/mock_wiring/`, each with `vlam_backend` set to `mock` and `reportable` set to false. `run_experiment.py` redirects mock `africot_full` runs to this directory so they never mix with reportable results.
- Two small example logs, `logs/example_outage_mock.jsonl` and `logs/example_incident_mock.jsonl`.

## Exact settings

From `africot/coordinator.py` and `africot/subgoal.py`:

- The slow loop is called every 300 simulated seconds and early when the novelty trigger fires.
- The novelty trigger compares the mean one-step world-model queue error over the last 10 decisions with twice the median of the 30 decisions before them, with at least 120 s between triggers.
- During a scenario outage window the last subgoal is held. After more than 600 s offline, the cached time-of-day schedule is used. Every connectivity switch is logged. The outage scenario runs from 1200 s to 2400 s of simulation clock time (`DEVIATIONS.md`).
- Each decision produces one log line with the fields required by the specification: simulation time, controller, scenario, seed, trigger, connectivity, backend, reasoning text, subgoal, plan, shield corrections and reason, applied phase and green, and the one-step error (`africot/log.py`).
- The slow loop is treated as instantaneous in simulated time, and its wall-clock latency is recorded only.

## How it was tested

The reviewer recorded 68 tests passing at the branch head, including `tests/test_slow_loop.py`, which covers scheduled calls, outage hold-last followed by the cached schedule, the novelty gap, the incident context window and a short end-to-end mock run (`reviews/S7.md`).

`results/mock_wiring/s7_integration_check.json` records `all_completed` as true and `total_safety_violations` as 0 for the 20 mock runs. Slow-loop calls per run ranged from 9 to 15 and parse failures were 0 in the check file. In the outage scenario on seed 0 the log shows `online`, then `offline_hold_last` at 1200 s, `offline_cached_schedule` at 1807 s and `online` at 2413 s, and the check file records the hold-then-cached sequence as true on all five seeds. The novelty trigger fired inside the incident window on all five seeds (first triggers at 1635 s, 1943 s, 1283 s, 1913 s and 1398 s for seeds 0 to 4).

The trigger is not specific to the incident. The same file records novelty events in normal (seeds 3 and 4), market (seeds 1, 3 and 4) and outage (seed 4). The reviewer found that the metric counts trigger events, and that a trigger can coincide with a scheduled call, so the number of distinct novelty calls is lower than the event count in some runs (market seed 4 has 4 events and 2 novelty calls, outage seed 4 has 4 events and 3 calls).

The reviewer reran incident seed 2 and outage seed 0 from scratch and found the metrics and coordinator events identical to the committed files, and the outage log byte-identical to `logs/example_outage_mock.jsonl` (`reviews/S7.md`).

## Deviations from the specification

No deviation is recorded for this stage in `DEVIATIONS.md`. The scenario event times are read as simulation clock times, which include the 300 s warm-up, as recorded for the stage on junction and scenarios.

## Reviewer findings and resolution

The stage was approved without required fixes (`reviews/S7.md`). Two low findings and two informational findings remain open as documentation points: the novelty metric counts events and not calls; the subgoal field `valid_for_s` is validated but not used, because the coordinator calls every 300 s whatever the model returns; the trigger also fires in scenarios without an event; and the instantaneous slow loop is an idealisation.

## Limitations

All numbers in this stage come from the mock backend and must not be presented as VLAM results. The mock waiting times are stored in the check file only to show completion. No Hugging Face run of `africot_full` is committed, so the benefit of the slow loop remains untested at the time of writing. The novelty trigger lacks specificity in the mock runs, and the instantaneous slow loop ignores the roughly 150 s per call reported for the 3B model on the CPU (`STATUS.md`).

## Dissertation paragraph

The integrated controller is designed to call the slow loop on a fixed schedule and whenever a world-model novelty signal fires, to hold or replace the subgoal during connectivity loss, and to log each decision for explanation. A wiring check with a deterministic mock model on four scenarios and five seeds completed all 20 runs without safety violations, showed the intended hold-last then cached-schedule sequence in the outage scenario, and showed novelty triggers inside the incident window on every seed, although the trigger also fired in scenarios without an incident (`results/mock_wiring/s7_integration_check.json`). These runs are intended only to verify wiring and are not reported as results of the vision-language-action model.
