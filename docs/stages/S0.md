# Stage S0: Environment and skeleton

## Purpose and place in the architecture

AfriCoT-VLA is designed as a slow loop (a vision-language-action model that reasons step by step and emits a subgoal), a fast loop (a latent world model and a cross-entropy-method planner) and a rule-based safety shield, all evaluated on a single Lagos-style T-junction in SUMO (see `SPEC.md`, goal and component descriptions, and `docs/design.html`). Stage S0 builds none of these components. It is intended to establish the reproducible foundation on which they are placed: a pinned software environment, a headless route to SUMO through TraCI, and the directory layout that later stages fill in. Because every later result is meant to be reproducible by the committed code, fixing the dependency versions at the outset is the first step towards the integrity rules in `SPEC.md`.

## What was built

The work was committed in `3c7821d` ("S0: environment, pinned requirements, package skeleton and TraCI smoke test") and consists of the following items.

- `requirements.txt`, which pins the CPU PyTorch wheel index and the packages used by later stages.
- `africot/__init__.py` and `africot/sumo_utils.py`, a small helper that locates the pip-installed SUMO binaries and sets `SUMO_HOME` from the `sumo` package when the variable is unset or invalid. The helper resolves tools such as `sumo`, `netconvert` and `netgenerate` from the `bin` directory of that installation and falls back to the system path. It never selects `sumo-gui`, so all runs are headless.
- `conftest.py`, an otherwise empty file whose presence places the repository root on the import path for tests.
- `tests/test_smoke.py`, the stage test described below.
- Placeholder directories `models/`, `results/`, `logs/`, `figures/` and `examples/`, kept in version control through `.gitkeep` files. The directories `sim/`, `africot/`, `tests/`, `reviews/` and `docs/` complete the layout given in the specification.
- `.gitignore`, which excludes bulky outputs such as `logs/*.jsonl` (except `logs/example_*.jsonl`), `sim/output/`, `*.safetensors` and `hf_cache/`, in line with the rule that large outputs are not committed.

## Exact settings

The pinned versions in `requirements.txt` are: eclipse-sumo 1.27.1, traci 1.27.1, sumolib 1.27.1, numpy 2.4.6, matplotlib 3.11.2, pytest 9.1.1, torch 2.14.1 (from the CPU wheel index `https://download.pytorch.org/whl/cpu`), transformers 5.19.0, accelerate 1.15.0, pillow 12.3.0 and qwen-vl-utils 0.0.14.

The smoke test generates a 2 by 2 grid network with `netgenerate` (grid number 2, grid length 100 m), defines one default vehicle type and one flow (begin 0, end 50, period 5 s, from edge `A0B0` to edge `B0B1`), starts `sumo` through TraCI with `--no-step-log` and `--no-warnings`, and advances 60 simulation steps.

## How it was tested

The builder recorded that the TraCI smoke test passed with one test in the suite (`STATUS.md`, S0 notes). The reviewer reran the stage independently on `32728a1` (`reviews/S0.md`): `pip install -r requirements.txt` exited with status 0, the installed versions matched the pins (eclipse-sumo, sumolib and traci 1.27.1, torch 2.14.1+cpu, transformers 5.19.0), and `pytest -q` reported 23 passed in 17.76 s. That count includes the tests from later stages that were already in the repository at review time; the S0 test itself is `tests/test_smoke.py`. The smoke test asserts that the simulation clock reads 60 s after 60 steps and that at least one vehicle appeared. The stage "done when" condition in `SPEC.md` (a working installation, a smoke test that runs a tiny SUMO simulation through TraCI, and the specified layout) is met on the reviewer's account.

No results files exist for this stage, since it produces no experimental numbers.

## Deviations from the specification

`DEVIATIONS.md` contains no entry for S0.

## Reviewer findings and resolution

The reviewer approved the stage with no required fixes (`reviews/S0.md`). One informational finding was recorded: in the review container, `pip` installed into `/usr/bin/python3` (Python 3.13) while the `python` on the path resolved to a different interpreter (3.11) without pytest. The reviewer judged this an environment property and not a repository defect, and advised that reproducers install and test with the same interpreter, for example through `python -m pip install -r requirements.txt`. No code change was made or needed.

## Limitations

The smoke test uses a generated grid network and not the project junction, so it checks the toolchain only and says nothing about the scenarios. The stage fixes versions that were current at build time; the requirement of Python 3.10 or newer in `SPEC.md` is not enforced by any file in the repository. The SUMO binaries are located through the pip package, so a system SUMO installation with a different version would be used only as a fallback.

## Text for the dissertation

The prototype is implemented in Python on top of the SUMO traffic simulator, driven headless through its TraCI interface. To support reproducibility, the software environment is intended to be fixed by a pinned requirements file that names SUMO 1.27.1 (with matching TraCI and sumolib packages), a CPU build of PyTorch 2.14.1 for the latent world model, and transformers 5.19.0 for the vision-language backend. The environment is designed to be verified by a smoke test that builds a small network, launches SUMO through TraCI and confirms that vehicles are simulated, and an independent reviewer reinstalled the pinned packages and reran the test suite successfully (`reviews/S0.md`). The repository layout separates simulation sources, controller code, tests, trained models, results, logs and figures, which is intended to keep every reported number traceable to committed code and data.
