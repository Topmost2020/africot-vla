AfriCoT-VLA Prototype Design

What gets built this week, how the parts connect, and how each one is checked before the experiments run. The prototype couples a VLAM with Chain-of-Thought reasoning to a latent world model through a subgoal, and runs on one Lagos-style T-junction in SUMO.

One decision cycle

What happens at each tick

Slow loopevery 300 sim-seconds, or earlier when triggered

  1. The renderer draws a top-down snapshot of the junction from SUMO vehicle positions, coloured by vehicle class.
  2. The coordinator checks connectivity. If the link is down, it keeps the last subgoal and skips the VLAM.
  3. The VLAM reads the snapshot plus context (clock time, market day, known incidents) and writes its reasoning step by step.
  4. It ends with a JSON subgoal. The validator parses it, clamps every value to a safe range, and keeps the previous subgoal if parsing fails.
  5. The subgoal and the full reasoning go to the log.

Fast loopat the end of every green phase

  1. Perception reads per-approach queue length, vehicle counts by class and occupancy from SUMO, then adds noise and missed detections.
  2. The CEM planner samples candidate plans (next phase and green time, three decisions ahead).
  3. The world model imagines the queues each plan would produce. The planner scores them with the cost the subgoal defines and refines toward the best.
  4. The safety shield checks the first step of the best plan and corrects it if it breaks a rule.
  5. TraCI applies the phase. The world model's prediction error is tracked; a sustained rise wakes the slow loop.

Interface

The subgoal: the only link between the two loops

The VLAM never sets signals directly. It sets what the planner should care about. The planner turns those weights into a cost and picks timings that minimise it under the world model's predictions.

Every field has a fixed range. A value outside the range is clamped, and an unreadable response keeps the previous subgoal, so a bad model output can only shift priorities within safe limits. The shield still applies after that.

The planner's cost for an imagined future is the weighted sum of approach queues, plus the pedestrian weight times pedestrian waiting, plus transit priority times the number of waiting danfos, plus a large penalty for any approach whose wait exceeds max_wait_s.

// example subgoal, market day afternoon
{
  "queue_weights": {
    "east": 1.0,      // 0.2 – 3.0
    "west": 1.0,
    "south": 2.2      // market side road
  },
  "pedestrian_weight": 1.8,   // 0.0 – 3.0
  "max_wait_s": 90,           // 45 – 180
  "transit_priority": 1.3,    // 0.0 – 2.0
  "valid_for_s": 300
}

Decisions

Assumptions and risks

Assumptions stated in the dissertation

  • One junction rather than a corridor, because of the timeline.
  • Simulation-only evaluation; real deployment is the roadmap.
  • The 8-layer framework keeps raw video on site, with the cloud as the full-connectivity tier.
  • SUMO counts plus noise stand in for the camera detector.
  • A rendered top-down image stands in for camera keyframes.

Risks and responses

  • VLAM slow on CPU. Use 3B only for tests; run experiments on Colab.
  • VLAM returns bad JSON. Validator keeps the last subgoal and logs the failure.
  • Colab disconnects. Save after every run; restart skips finished runs.
  • World model inaccurate. Report it honestly; the "without world model" ablation shows its effect.
  • Gridlock in SUMO. Tune demand on Tuesday before any learning.

The prototype tests the core claim: a reasoning model that sets priorities, coupled to a world model that plans, works as one closed loop and keeps working when the reasoning side is unreachable. The corridor, tiered communication and field deployment are designed and described, not built.
